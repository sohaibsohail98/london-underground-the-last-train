Repo: london-underground-the-last-train, branch off main. This is LAST TRAIN, a first person zombie survival game on a fictionalised London Underground line, built in Unreal Engine 5.8. Read CLAUDE.md at the repo root first, in full, for every project convention: British spelling everywhere including comments and docs, never use em or en dashes anywhere (source, docs, this branch's own commit messages), TObjectPtr not raw UObject* in containers, LT_LOG not UE_LOG, no TODO/FIXME/HACK markers, clang-format 20 with tab indent, headers begin with #pragma once and end their include list with X.generated.h. You have no access to the Unreal Editor and cannot compile or run PIE: write C++ against the existing module conventions, do not attempt to build or test it in-engine, and say so plainly in your summary rather than claiming it compiles.

Context, so this branch does not collide with sibling work: three other remote branches exist alongside this one, each adding a Source/ hook this project currently lacks - claude/phase-g1-audio-prompt (weapon/zombie/train sound hooks), claude/pause-menu-prompt (pause input), claude/save-settings-prompt (disk save and settings persistence). A fourth sibling, docs/tasks/remote-brief-subtitles.md on its own branch, adds a subtitle display system that will want to read the same zombie vocal cue points this branch's decal spawning reads, so name and place things in a way a later merge of both onto main will not fight over the same hook (see "Coordination with the sibling subtitle branch" below). A fifth sibling, docs/tasks/remote-brief-melee.md on its own branch, adds a melee system whose finishing hits should also spawn gore through the same system this branch builds - read that brief's summary of what it expects from you, in the section below, so this branch's public API is usable from a melee hit as well as a hitscan one.

Task: build the blood and gore decal system that docs/art-direction.md section 6 already specifies as a design principle with zero Source/ implementation. Read docs/art-direction.md section 6 in full first, it states the actual design intent (restrained, not excessive, pooled/instanced decals, capped and recycled rather than accumulating without limit) - do not invent a different visual philosophy, implement that one. Read Source/LastTrain/Public/Zombies/LTZombieCharacter.h in full: it already has the two hook points this system attaches to, OnHitReaction(const FHitResult& Hit, bool bHeadshot) (a BlueprintImplementableEvent, fired per hit, carries impact location and normal) and OnDeathPresentation(bool bHeadshot) (fired on death, already documented in its own comment as "the Blueprint hook for the death montage and gore" - this branch is what finally answers that comment). Also read Source/LastTrain/Public/Weapons/LTWeaponComponent.h's TracePellet and OnHitConfirmed for how a hit is resolved today, so the C++ trigger point you add sits at the correct layer (the zombie character reacting to being hit, not the weapon component, since a melee hit from the sibling branch also needs to trigger the same gore, and melee will not go through ULTWeaponComponent's hitscan path).

Scope:

1. A pooled decal spawner. Add a new small system, likely a UWorldSubsystem or a UGameInstanceSubsystem (check which is more appropriate for something that needs to exist exactly once per world and persist across a round without being tied to any single actor - say which you chose and why), Source/LastTrain/Public/Combat/LTGoreDecalSubsystem.h (new Combat/ folder if one does not exist yet, matching the module's existing category-folder convention: Weapons/, Zombies/, Rounds/, Economy/, Interaction/, Train/, Core/, Player/). It should expose a UFUNCTION(BlueprintCallable) SpawnBloodDecal(FVector Location, FVector Normal, bool bHeadshot) or similar, that spawns a decal component at the given transform and recycles the oldest one once a configurable maximum decal count is reached (EditDefaultsOnly, sensible default, name it MaxActiveDecals or similar), matching art-direction.md's "capped and recycled" rule exactly, not an unbounded accumulation.
2. Wire ALTZombieCharacter's existing OnHitReaction and OnDeathPresentation native implementations (check whether these currently have any C++ body at all beyond the BlueprintImplementableEvent declaration, or whether they are purely Blueprint hooks today - if purely Blueprint, add the native call to the new subsystem's SpawnBloodDecal alongside the existing Blueprint event broadcast, do not remove the Blueprint hook, both should fire) to call into the new subsystem on a body hit, and with a more pronounced effect (more decals, or a distinct death-pool decal type, your judgement, keep it restrained per the design principle) on death.
3. A UPROPERTY on the subsystem or ULTZombieTypeData (check which is more correct: a global decal material set on the subsystem versus a per-type override, and prefer the subsystem holding one shared, restrained material set unless there is a clear reason a type needs its own, since art-direction.md's restraint principle argues against per-type gore variation) for the decal material(s) to use, null-safe defaults, following this project's established "null until a Blueprint or data asset assigns it" pattern throughout.
4. Coordination with the sibling melee branch: read docs/tasks/remote-brief-melee.md once it exists on its own branch (if you are working before that branch lands, read this file's own description of it below instead). The melee system needs to call the same SpawnBloodDecal or equivalent public entry point this branch builds, from a melee hit that does not go through ULTWeaponComponent. Make sure your public API takes a location, a normal and a headshot/critical flag as plain parameters (not a struct only the weapon component can build), so it is trivially callable from any hit source, hitscan or melee.
5. Write a short new task spec, docs/tasks/phase-h2-gore-system.md, telling CC-in-Unreal what remains: assigning an actual decal material (the project's existing surface materials under Content/LastTrain/Surfaces/ may already have a blood-adjacent variant from the zombie surface mask work on tools/zombie-surfaces/, check docs/tasks/phase-f6a-zombie-surface-masks.md for whether any of those masks are reusable as a world decal texture rather than only a character skin mask - if genuinely reusable, say so and point at the exact asset; if not, say a new decal texture needs sourcing or authoring), tuning MaxActiveDecals against the horde's 24-alive cap for performance (this project already has documented sensitivity to per-zombie-instance cost at high horde counts, see the crowd performance notes in docs/tasks/handover.md and the 60fps gate in docs/tasks/README.md's Phase B row - flag this explicitly in the spec as a performance-sensitive number, not an arbitrary one), and confirming the restrained visual read in PIE against art-direction.md's stated intent.

Rules: British spelling, no dashes, TObjectPtr not raw pointers, LT_LOG not UE_LOG, no TODO markers, GENERATED_BODY present, headers end their includes with X.generated.h. No gore beyond what a 12-rated-adjacent restrained treatment implies, per art-direction.md's own stated tone, this is not a gore-forward game. Keep commits small: the subsystem as one commit, the LTZombieCharacter wiring as a second, the spec doc as a third.

When done: do not merge or push anything, just leave the branch in a clean, reviewable state. Report back the exact new public API (class name, function signature, key UPROPERTY names and defaults), which subsystem type you chose and why, and explicitly flag anything you were not confident about rather than guessing silently.
