# Remote brief: PCG surface dressing (authoring-time only)

This file is the handoff prompt for a remote Claude session working this
branch, verbatim. Follow it as the task brief.

---

Repo: london-underground-the-last-train, branch off main. This is LAST TRAIN, a first person zombie survival game on a fictionalised London Underground line, built in Unreal Engine 5.8. Read CLAUDE.md at the repo root first, in full, for every project convention: British spelling everywhere including comments and docs, never use em or en dashes anywhere (source, docs, this branch's own commit messages). You have no access to the Unreal Editor and cannot compile, run PIE, or open any PCG graph asset. This branch is a design/spec document only, not a working PCG graph: a PCG Graph is a `.uasset`, it cannot be authored as text in a way a later editor session can just import, so do not attempt to fake one. Your deliverable is a precise, actionable specification that CC-in-Unreal (the session with editor access) builds the actual PCG graph from.

Context, and the boundary this branch must not cross: a broader "use PCG/MassEntity to automate the whole game" proposal was considered and explicitly rejected for this project. Read CLAUDE.md's module table and docs/tasks/README.md's Phase B/D status rows first: `ALTZombieCharacter` is a full `ACharacter` on a jittered repath cadence (already built, already PIE-verified, deliberately not a behaviour tree, deliberately not MassEntity - the crowd cap is 24 and the current perf bottleneck is documented as GPU-bound, not CPU-bound, so a MassEntity rewrite would not even address the real cost), and the station layouts (`L_CanaryWharf_Greybox`, the Paddington pass) are hand-composed around fixed gameplay beats (spawn points, sightlines, wall buy placement, the "one side closed, one side open" composition rule) and factual real-station identity, not generated layouts. Do not propose PCG for zombie behaviour, zombie spawning, station layout, room connectivity, or any gameplay-relevant actor placement. This branch is strictly authoring-time visual dressing: cables, grime, small clutter, decals, scattered along surfaces that are already fixed by the time PCG runs.

Read docs/art-direction.md in full, especially section 6 (wear and grime principles) and whatever the document says about clutter/dressing density, so the dressing philosophy matches the project's established restraint rather than over-scattering. Read docs/reference/reference-frame-notes.md for what the visual target actually shows (cable runs, grime patterns, wear) versus what must not be copied. Read docs/tasks/phase-f1-modular-kit.md for the existing kit mesh set (wall panel, floor panel, ceiling panel, pillar, platform edge, tunnel portal, stairs, bench, bin, handrail) so the dressing spec knows what surfaces already exist to scatter onto, and read docs/reference/canary-wharf-grid.md so the spec can call out zones that must stay clear (wall buy anchors, spawn points, the boarding zone, any sightline the round-pacing work depends on - cross reference docs/tasks/phase-h1-zombie-pacing-balance.md's point about spawn point sightlines needing to stay clear of visual clutter that could hide or obscure a zombie's read, and make sure the dressing spec explicitly excludes those zones rather than scattering blindly over the whole level).

Scope: write docs/tasks/phase-f1a-pcg-dressing.md, a new task spec for CC-in-Unreal, covering:

1. **Ceiling cable runs.** A PCG graph fed by a spline drawn along the ceiling by hand (the spline itself is placed by CC-in-Unreal per station, following the ceiling's actual run, not generated), spawning cable bundle segments, junction boxes, and sagging wire meshes at intervals along it. Specify: what mesh assets this needs (check whether anything cable-like exists in the already-staged _incoming_assets/ pools referenced in docs/reference/asset-sources-phase-f.md, or state plainly that new simple cable/junction-box meshes need modelling, this is a small greybox-able asset, not a hero mesh), a sensible spacing/randomisation range, and a rule that the spline stays clear of the train's swept volume and any interactable actor's collision.
2. **Wall-floor intersection grime and clutter.** A PCG Surface Sampler (or equivalent volume/spline based sampler, your call on which PCG node best fits scattering along a floor-wall seam rather than a spline) that scatters small grime decals and litter meshes along wall-floor intersections, explicitly excluding a buffer radius around every wall buy anchor (per canary-wharf-grid.md's `W` tiles), every spawn point, and the boarding/train-adjacent zone, so gameplay-critical readability is never contested by clutter. State the exclusion mechanism precisely (a PCG exclusion volume keyed to actor tags or a manually painted exclusion mask, your call, explain the tradeoff briefly) rather than leaving it as a vague instruction.
3. **Do not implement the "medical debris near Screamer spawn points" idea from the original discussion.** That ties dressing density to gameplay data (`ULTZombieTypeData`) at what would need to be runtime or per-round PCG execution, which reintroduces exactly the runtime-coupling risk this brief exists to avoid (a station's dressing changing based on round composition is a gameplay-adjacent system, not authoring-time set dressing). If genuinely wanted later, it is a separate, larger proposal requiring a design decision, not something to fold into this spec. State this exclusion explicitly in the spec you write, so nobody reintroduces it by mistake.
4. **Determinism and version control.** State plainly in the spec that PCG graphs can be set to bake to static instances (turning generative placement into fixed, committed instanced static mesh data) versus staying runtime-generative, and recommend baking for this project: a shipped, once-placed station should not regenerate its dressing on every level load (matches this project's existing "static instances over dynamic generation" instinct already used for the zombie surface masks work, see docs/tasks/phase-f6a-zombie-surface-masks.md's own step 2 title "uses static instances"). Say this explicitly rather than leaving PCG's runtime-versus-baked choice ambiguous.
5. **Verification.** A Map Check pass after baking (`MAP CHECKDEP NOCLEARLOG`, console `MAP CHECK` is banned per CLAUDE.md), and a read-back confirming no PCG-scattered mesh overlaps or occludes any gameplay actor, wall buy, or the spawn-point sightlines flagged in phase-h1-zombie-pacing-balance.md.

Do not write any other file. Do not propose extending this into zombie behaviour or level layout at any point in the document, that boundary is the entire point of this branch existing as a narrower, corrected version of a broader idea that was already rejected.

When done: do not merge or push anything, just leave the branch in a clean, reviewable state (one new markdown file). Report back a one paragraph summary of the spec's scope and explicitly confirm you did not stray into zombie behaviour or layout generation.
