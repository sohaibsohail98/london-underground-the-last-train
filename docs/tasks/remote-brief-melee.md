Design decision this branch makes, stated so it is not re-litigated: a simple contextual melee strike, not a dedicated weapon slot, not a knife with its own ammo or equip state. Triggered by a MeleeAction input while any weapon is held (a bash/shove with the current weapon, not a separate knife model), because this project's weapon roster (docs/reference/phase-h1-loadout-draft.md) has no melee weapon designed and adding one is a larger scope than this gap needs to be closed at. This mirrors how many genre peers implement melee as a quick weapon-bash rather than a fully modelled secondary weapon. If you disagree with this framing after reading the existing docs, implement it as specified anyway and note your disagreement in the final report rather than deciding unilaterally to build something larger.

Scope:

1. Add a MeleeAction UInputAction property to ALTPlayerCharacter, same pattern as the existing actions.
2. Add a UFUNCTION(BlueprintCallable) PerformMelee() that traces a short range melee hit (shorter than the equipped weapon's MaxRange, a fixed close range constant is fine, name it something like MeleeRange with a sensible default such as 150 units, EditDefaultsOnly on the character or the weapon component, your call which, say why) directly ahead of the camera, applies a fixed melee damage value (do not scale it off the held weapon's BaseDamage, keep it a simple flat value, EditDefaultsOnly, so melee is a consistent panic button regardless of what is equipped) via the same ApplyDamage path ULTWeaponComponent's TracePellet uses today (read that function's body carefully and match its damage application call exactly, do not diverge into a different damage type), and calls the gore subsystem's SpawnBloodDecal-equivalent entry point from the sibling branch on a hit.
3. A short cooldown between melee strikes (EditDefaultsOnly float, e.g. 0.8s default) so it cannot be spammed as a substitute for the weapon's own fire rate, checked the same way ULTWeaponComponent already gates fire rate via TimeUntilNextShot, mirror that pattern rather than inventing a new one.
4. Bind MeleeAction in SetupPlayerInputComponent, same block style as the other bindings.
5. Fire a UPROPERTY(BlueprintAssignable) delegate on a successful melee hit (FOnMeleeHitConfirmed or similar, mirroring ULTWeaponComponent's existing FOnHitConfirmed naming and shape) so a HUD or animation Blueprint can react, matching the existing OnHitConfirmed/OnAmmoChanged delegate pattern rather than requiring a poll.
6. Melee should work whether or not the equipped weapon has ammunition, since its entire purpose is a fallback when a player runs dry - do not gate PerformMelee() on Magazine or Reserve counts, only on its own cooldown and whatever ELTRunState checks are appropriate (no melee once Dead, consistent with how docs/tasks/remote-brief-pause-menu.md gates its own pause action on run state - read that file's run-state-check paragraph and mirror the same reasoning here for consistency across the sibling branches).
7. Write a short new task spec, docs/tasks/phase-h3-melee-presentation.md, telling CC-in-Unreal what remains: binding MeleeAction to a key in the Enhanced Input asset, an animation for the bash/shove (this depends on whichever FP arms mesh phase-h-weapon-presentation.md's asset sourcing lands on, cross reference docs/reference/asset-sources-phase-h.md, note that a melee swing animation was not in that document's scope and needs its own quick sourcing check or hand authoring, same "hand author over sourcing a pack" recommendation that document reached for fire and reload), and a melee impact sound once docs/tasks/phase-g1-audio.md's hooks exist (cross reference that spec once it exists from the audio branch, or note it as a future hook if this branch lands first).
